# 40 — 維護協議(怎麼安全地更新這套檔案)

> 讀者:未來的主模型。這套檔案(CLAUDE.md + docs/claude/*)是制度本體,
> 改壞的代價是之後每個 session 一起變笨 —— 所以改法有規矩。

## 1. 可以自行改(不用問使用者)

- **追加踩坑教訓**(第 3 節格式)到對應檔案。
- **為新的 ref 檔在 CLAUDE.md 路由表加一行**(含觸發條件)。
- **修正已被 live 探測證偽的事實**(例:文件說欄位存在但 DB 沒有)——
  修正時保留一行「(原記載 X,2026-MM-DD 探測證偽)」。
- **給過時內容加日期標記**(「疑似過時 2026-MM-DD,依據:…」),不刪。
- **60-TRIGGERS.md 的觸發狀態更新**(達成/未達成/已執行)。

## 2. 動之前必先問使用者

- 刪除或弱化任何 **NEVER / MUST / 鎖定 / verbatim 引言** 級規則
  (包括「看起來過時」的 —— 過時與否由創辦人判)。
- 改 North Star 文字、品牌鎖定句。
- 把 `10-DISPATCH.md` 的門檻/次數規則改動超過 2 倍。
- 整檔重寫或合併檔案。
- 免費/付費界線、送審/帳密紅線 —— 這兩條連問都要引原文問。

## 3. 踩坑教訓的格式與去處

格式(≤6 行,一坑一條):
```
- [2026-MM-DD] 觸發:{什麼情況下踩到} → 規則:{以後怎麼做,可執行的一句}
  例:{真實案例一句,含檔名/commit/錯誤訊息關鍵字}
```

去處(寫錯地方 = 沒人會再看到):

| 教訓類型 | 寫進 |
|---|---|
| 演算法/標籤/排序 | ref-tag-algorithm.md 末尾「踩坑補遺」節(沒有就建) |
| 創辦人偏好/UX 判斷 | ref-founder-style.md 末尾補遺節 |
| CI/migration/DB/外部服務 | ref-infra-ops.md 末尾補遺節 |
| 既有功能的行為契約 | ref-product-history.md 對應段落附近 |
| 派工/驗收/模型選擇 | 10-DISPATCH.md 或 20-JUDGMENT.md 對應節 |
| 天天都會踩的(跨類型) | CLAUDE.md 硬規則區(最貴的位置,想清楚再放) |

## 4. 備份規則

- **結構性改動**(重排、刪節、合併、重寫)→ 先
  `cp {檔} docs/claude/archive/{檔名}-{YYYY-MM-DD}.md` 再動手。
- **純追加**(教訓、路由行、狀態更新)→ git 即備份,不用另存。
- archive/ 只進不出;要清也是問過使用者。

## 5. 膨脹回收(觸發即執行,不用問)

- CLAUDE.md **> 250 行** → 把最不常用的硬規則細節下放 ref 檔,只留一句
  + 路由(下放哪些自行判斷,但 NEVER 級的一句版必須留在 CLAUDE.md)。
- 任一 ref 檔 **> 900 行** → 按主題拆兩檔,路由表同步更新。
- 同一補遺節 **> 15 條教訓** → 合併同類、刪已被制度化(已寫進硬規則)的。
- 回收屬「結構性改動」→ 按第 4 節先備份。

## 6. 改完必驗(不可省)

任何對 CLAUDE.md 或 docs/claude 的修改,完成後:
1. 用 `30-TEMPLATES.md` 模板 5 派 fresh-context 驗收 agent,驗:
   路由表路徑全存在、無互相矛盾的規則、新內容無模糊語句。
2. read-back:`wc -l` + 抽讀改動段,確認落地完整。
3. commit + push(訊息前綴 `docs(agent-os):`),制度檔不落遠端 = 沒改。
