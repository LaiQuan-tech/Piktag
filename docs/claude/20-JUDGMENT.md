# 20 — 判斷力外化(rubric 與 checklist)

> 讀者:未來的主模型。每節 = 一個判斷點:判準 → 正例 → 反例。
> 正反例全部取自本專案真實歷史,可以在 git log / ref 檔查證。

## 1. 何時該升級模型(或加派第二意見)

**升級判準(命中任一即升)**:
- 同一子任務照 `10-DISPATCH.md` 第 5 節的次數規則觸頂。
- 錯誤會**放大**:一支錯的 migration 卡死整條 CI、動到鎖定契約、
  不可逆操作(刪資料、對外發布)。
- 問題需要「跨兩個以上子系統的因果鏈」才解釋得通(例:client 行為異常
  但根因在 edge fn 的 config)。

**正例**:2026-06-06 pgvector `<=>` 42883 —— 錯誤訊息指向函式不存在,但
真因是 `search_path` 少了 `extensions`,而且它 block 了後面整疊 migration。
這種「錯誤訊息在 A、根因在 B、影響在 C」的題,直接上最強模型並附完整軌跡。
**反例**:tsc 報 `c.surface 不存在於 ColorPalette` —— 訊息即答案(改用
c.white),升級是浪費。**錯誤訊息已經包含修法的,不升級。**

## 2. 何時算「真的完成」

**完成 = 全部打勾,缺一項就不能對使用者說「完成」:**
- [ ] tsc 0 錯(mobile 或 root,看改哪邊)
- [ ] commit + push,CI 綠(migration 改動要看到 Supabase Deploy: success)
- [ ] **功能級驗證**:DB 改動 → live 探測讀回實際值;admin/web → 打 API 或
  RPC 驗回傳形狀;RN UI → tsc + 說明在裝置上驗什麼(瀏覽器驗不到 RN)
- [ ] 對使用者的總結:改了什麼、驗了什麼、**沒驗到什麼**(明說)

**正例**:官方帳號換標籤 —— push 後等 CI 綠,再用 service key 直接查
piktag_user_tags 確認十個標籤 + 順序 + bio 都在,才回報完成。
**反例**:clear-stale-badges cron —— push 成功、CI 綠,但 config.toml 少了
`verify_jwt = false`,功能是死的。「推上去了」不是完成,**「讀回來對了」才是**。

## 3. 何時該停下來問使用者

**必問(不問是缺陷)**:
- 不可逆或對外:刪資料、force push、商店送審/發布、寄信/發文、花錢。
- 範圍變更:做著做著發現要動使用者沒提的模組/契約才能完成。
- 契約互撞:兩條鎖定規則衝突,或使用者的要求違反鎖定契約
  (先引契約原文推回,讓使用者裁決 —— 這就是中肯)。
- 多台裝置/帳號/瀏覽器等**只有使用者知道**的環境事實。

**不准問(自己決定並在回報中說明)**:
- 有慣例預設的技術選擇(命名、檔案位置、要不要跑 tsc)。
- 可逆且在原請求範圍內的實作細節。

**正例**:六台 Chrome 連著,選哪台 → 問(只有使用者知道哪台登入了)。
**反例**:「要不要先備份再改?」→ 不問,備份本來就是規則,直接做。

## 4. 什麼訊號代表方向錯了(換路,不是重試)

**換路訊號(命中任一,停止同法重試)**:
- 修 A 冒出 B、修 B 冒出 C,錯誤在**不相關的檔案**擴散。
- 每次「快好了」但 diff 已膨脹到原估計的 3 倍。
- 需要修改鎖定契約才能讓現在的做法成立。
- 調參數式的重試(加大、調高、多等)連兩次無效 —— 代表機制錯了,
  不是參數錯了。

**換路動作**:回滾到乾淨點 → 用一句話重述問題本質 → 列出 ≥2 條不同機制的
路 → 選一條或按第 3 節upgrade/問人。
**正例**:2026-06-26 偽 3D 人脈圖 —— AnimatedLine 畫不出線,調 stroke/opacity
兩次無效(線根本沒在 render,不是太淡)。正確動作是整個回退 2D 重做,
當天執行。**反例(不要學)**:如果當時繼續第三輪調透明度,就是把機制問題
當參數問題 —— 那正是換路訊號出現的樣子。

## 5. 品質底線怎麼驗(按產物類型)

| 產物 | 底線檢查(全過才算過) |
|---|---|
| i18n 改動 | 腳本化 + assert 19/19 + diff --stat 每檔行數符合預期 |
| migration | 冪等寫法;時間戳 > 現有尾巴;涉及的欄位先 live 探測;push 後看 Deploy 綠 |
| RN UI | tsc 0;dark-mode 固定底/前景配對檢查;該頁鎖定 CTA 未被競爭;共用元件未被複製 |
| 通知類 | 四點檢查逐項 grep(type 名在 4 個檔案出現);SQL body 非空 |
| 排序/媒合面 | 四點檢查(分管線/分區/dismissals/is_official);搜尋權重動了 → 有 replay 證據嗎 |
| 文案 | 字數上限(店面 4000/170/30);無 emoji;品牌鎖定句未被翻譯;範例城市按市場 |
| 對 DB 的任何斷言 | 探測過才寫;文件與探測衝突以探測為準並回寫修文件 |

## 6. 誠實條款 —— 這套制度補不了的東西

拆解、驗證、多樣本評審能補**執行品質**;以下補不了,遇到照寫的做:

- **品味與模糊題**(文案語氣、設計美感、產品取捨、「哪個比較對」):
  弱模型的處理法 = (1) 給出**帶推薦的選項**(推薦 + 理由 + 1-2 個替代),
  讓創辦人裁決;(2) 事關重大時用多樣本:3 個獨立版本 + judge agent 評優,
  但要明說「這是近似,不是品味」;(3) 絕不假裝有把握 —— 低信心就寫低信心。
- **創辦人語感**(中肯的力度、什麼時候該堅持):ref-founder-style 的 verbatim
  引言是校準器,拿不準就引原文問「這條契約適用嗎?」。
- **沒有測試覆蓋的深層互動 bug**:驗證只能到「讀回來對了」;真機行為要
  創辦人跑 SMOKE_TEST.md。明說這個邊界,不要宣稱替代。
