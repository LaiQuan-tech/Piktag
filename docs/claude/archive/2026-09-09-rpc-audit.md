# SECURITY DEFINER RPC 曝露稽核（2026-09-09,只調查未改檔）

所有行號皆為「時間戳最大的那份定義」。已逐一比對同名函式的多次
CREATE OR REPLACE / DROP,取最新。

---

## 0. 先講最重要的機制發現(這會決定所有修法)

**`REVOKE ... FROM PUBLIC` 在 Supabase 不夠。** Supabase 平台在 bootstrap 時對
`schema public` 設了 `ALTER DEFAULT PRIVILEGES ... GRANT ALL ON FUNCTIONS TO
anon, authenticated, service_role`,所以每支新函式除了 PUBLIC 的隱含 grant,
還會拿到一份**寫死在 proacl 裡、指名 anon / authenticated 的 grant**。只 REVOKE
FROM PUBLIC 不會動到那份。

證據(repo 內自證,不需連線):

- 下列 8 支在 migration 裡**明明白白 REVOKE FROM PUBLIC 過**,linter 卻仍然報:
  - `check_username_available` — `20260605010000_username_availability_rpc.sql:54`
  - `bump_tag_search_count` — `20260526010000_tag_search_count_ranking.sql:64`
  - `qr_group_member_count` — `20260508130000_qr_groups.sql:73`
  - `qr_group_members` — `20260508130000_qr_groups.sql:108`
  - `is_notification_category_enabled` — `20260702170000_tag_suggest_nudge.sql:139`
  - `select_tag_nudge_due_users` — `20260702170000_tag_suggest_nudge.sql:244`
    以及 `20260705030000_test_accounts.sql:415`
  - `trigger_tag_suggest_nudge` — `20260702170000_tag_suggest_nudge.sql:285`
  - `is_test_account_user` — `20260705030000_test_accounts.sql:60`
- 而 repo 裡**唯一寫對的那份** migration 自己就在註解裡講明了差別:
  `20260626000000_lockdown_internal_function_grants.sql:83`
  → `REVOKE EXECUTE ON FUNCTION %s FROM PUBLIC, anon, authenticated`
  然後 `GRANT ... TO postgres, service_role`。

**所以任何修法都必須用三角色形式**:
`REVOKE ... FROM PUBLIC, anon, authenticated` + 再 `GRANT` 回真正需要的角色
(service_role / authenticated),不能只寫 `FROM PUBLIC`。

（唯一未 100% 確認的一環是 Supabase 的 default privileges 本身不在本 repo 內
(平台 bootstrap 設的),我沒有連線探測。若要一擊確認,跑
`SELECT proname, proacl FROM pg_proc WHERE proname='bump_tag_search_count';`
看 proacl 是否含 `anon=X/postgres`。)

## A. 真的該修

依風險排序。

### A1. `resolve_pending_connections(p_new_user_id uuid, p_scan_session_id text)` — 最高
- 檔案:`20260513090000_vibe_tags_host_side_only.sql:28`(尾行 `$$ LANGUAGE plpgsql SECURITY DEFINER;`,第 1892 行位置)
- **完全沒有任何 auth 檢查**。`p_new_user_id` 是呼叫者自己傳的參數,函式從頭到尾
  沒讀過 `auth.uid()`。
- 匿名可做的事:給定任一還在 `status='pending'` 的 `scan_session_id`,
  **寫入兩筆 `piktag_connections`(雙向好友)**、寫 `piktag_connection_tags`、
  把 pending row 標 resolved、把 `piktag_scan_sessions.scan_count` +1。
  也就是說可以把任意 user id「塞成」某個 QR 主人的好友。
- 唯一門檻是要猜到 scan_session_id(uuid)與 host 的 user id,但兩者在公開分享
  連結 `pikt.ag/u/<username>?sid=<uuid>` 裡就有 —— 這不是秘密。
- 唯一 caller:`mobile/src/navigation/AppNavigator.tsx:893`(已登入才跑)。
- 建議:函式內加 `IF auth.uid() IS NULL OR auth.uid() <> p_new_user_id THEN
  RAISE EXCEPTION ...`(不要只 revoke —— 目前 authenticated 也能冒充別人),
  同時 `REVOKE ... FROM PUBLIC, anon, authenticated` + `GRANT TO authenticated`。

### A2. `select_tag_nudge_due_users(p_limit int)` — 高(PII 外洩)
- 檔案:`20260705030000_test_accounts.sql:327`
- 無任何 auth.uid()。回傳每列含 **`push_token`、`bio`、`full_name`、`headline`、
  `language`、既有標籤、已移除標籤** —— 一次最多 `p_limit` 筆,而 `p_limit` 由
  呼叫端控制(可傳很大的值)。這等同一支「匿名匯出使用者名單 + 推播 token」的 API。
- 只有 cron / edge fn 該呼叫。migration 已想 revoke(`20260702170000:244` /
  `20260705030000:415`)但用了 PUBLIC-only 形式,見第 0 節。
- 建議:三角色 REVOKE + `GRANT TO postgres, service_role`。

### A3. `trigger_tag_suggest_nudge()` — 高(可被匿名觸發花錢 + 推播)

- 匿名可做的事:**無限次觸發整批 Gemini 標籤生成 + 對真實使用者發推播**。
  帳單與騷擾雙殺。
- migration 已 revoke 但是 PUBLIC-only(`:285`)。
- 建議:三角色 REVOKE + `GRANT TO postgres, service_role`。

### A4. `bump_tag_search_count(p_tag_ids uuid[])` — 中(排序訊號污染,North Star 相關)
- 檔案:`20260526010000_tag_search_count_ranking.sql:53`
- 純 SQL,`UPDATE piktag_tags SET search_count = search_count + 1 WHERE id = ANY(...)`,
  **零檢查、零去重、零速率限制**。
- 影響為什麼是真的:同檔 `:43` 有 generated column
  `popularity_score = COALESCE(usage_count,0) + 2 * COALESCE(search_count,0)`,
  `search_count` **權重是 usage_count 的兩倍**,SearchScreen 依此排序
  (`mobile/src/screens/SearchScreen.tsx`,唯一 caller 在 `:2307`)。
  匿名可把任意 tag 推到搜尋頂端 —— 直接打在 North Star(標籤品質)上。
- 注意:即使 revoke 掉 anon,**任何已登入使用者仍可任意灌**(現有 grant 就是
  `TO authenticated`)。真正的修法要在函式內加去重/節流(例如以
  `auth.uid()` + tag 為 key 的 N 分鐘內只計一次),revoke anon 只是止血。
- 建議:三角色 REVOKE + `GRANT TO authenticated, service_role`;另外開一張
  「加節流」的後續票。

### A5. `is_admin(p_user_id uuid DEFAULT auth.uid())` — 中

- `SELECT EXISTS (... FROM public.admins a JOIN auth.users u ON LOWER(u.email)=LOWER(a.email) WHERE u.id=p_user_id)`。

- 沒有任何 client 端呼叫(mobile / landing / admin 的 `.rpc()` 清單裡都沒有);
  它是 RLS policy 的內部 helper,RLS 求值時本來就以 definer 身分跑,revoke 不影響。
- 建議:三角色 REVOKE + `GRANT TO postgres, service_role`。

### A6. `popular_tags_near_location(p_location text, p_limit int)` — 低到中

## C. 有內部防衛,revoke 只是收緊,不急

`block_user`, `fetch_ask_feed`, `fetch_inbox`, `fetch_my_active_ask`,
`find_connections_by_tag`, `get_badge_count`, `get_chat_unread_summary`,
`get_friend_graph`, `get_friend_of_friend_ids`, `get_my_removed_tag_names`,
`get_or_create_conversation`, `mark_conversation_read`, `qr_group_members`,
`set_conversation_folder`, `touch_last_active`, `vibe_member_current_tags`,
`event_attendees`, `set_event_visibility`, `get_contact_bridges`,
`record_ask_response`, `check_username_available`

補三點:
- `record_ask_response`(`20260527010000_ask_response_tracking.sql:73`)靠的不是
  函式而是 schema:`responder_id uuid NOT NULL`(同檔 `:12`),匿名寫入時
  `auth.uid()` 為 NULL → NOT NULL 違反,insert 失敗。防衛是真的,但是**間接的**。
- `check_username_available`(`20260605010000:28`)匿名呼叫會正常回答 true/false,
  嚴格說是個 username 枚舉 oracle;但那是這個功能的本質(任何註冊表單都有),
  且無 anon caller,revoke anon 安全無風險。
- `get_contact_bridges` 是唯一已經用對形式的
  (`20260712010000_contact_bridges.sql:60` = `FROM public, anon`)。

`get_scan_session_public` 另有一個獨立小問題:它**沒有 `SET search_path`**
(`20260521000000:22-24` 只有 `SECURITY DEFINER STABLE`),是另一條 lint
(`function_search_path_mutable`)。順手補 `SET search_path = public, pg_temp`。
